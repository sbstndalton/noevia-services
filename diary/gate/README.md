# Diary synthetic gate

Release gate for the Diary service, run against an isolated `diarygate` stack on the MS-01 with an
invented corpus. **Never use real Diary data**: everything here is generated by `gen_fixture.py`
(a fictional cartographer, fictional people and places, no credentials).

## Pieces

| File | What it does |
| --- | --- |
| `gen_fixture.py` | Deterministic fixture: 60 daily files (`Entries/YYYY/Month/Month D, YYYY.md`, the diary's own daily layout, byte-identical to what its writer produces), 180 entries, 60 ground-truth queries, 11 scripted mutations, `manifest.json` with per-file sha256, tree hash, seed, anchor, query clock (an empty trailing day 61, 12:00Z) and generator commit. Same arguments, same bytes (`tests/test_gate_fixture.py`). |
| `compose.yml` | Project `diarygate`: the diary image built from `git archive <rev>`, network `diarygate_net`, volumes `diarygate_data`, `diarygate_corpus` (gate diary) and `diarygate_nomodel_data`, `diarygate_nomodel_corpus` (no-model diary, inference always disabled), `DIARY_RETRIEVAL_TRACE=1`, `CORPUS_BACKEND=local`, `TZ=UTC`, port on 127.0.0.1 only. No WebDAV or other remote file storage, S3, bind mounts or production volumes. |
| `env.gate.example` | Key names only. |
| `make_env.sh` | Writes the gitignored `.env.gate` (mode 600) with fresh random `DIARY_TENANT_KEY` and `DIARY_AUTH_TOKEN`; inference URLs from `GATE_*` variables, or an unresolvable name with `--no-inference`. Prints key names only. |
| `up.sh` / `down.sh` | `up.sh --rev` refuses if diarygate volumes already exist, builds and starts at that revision, then `isolation.py up` checks with `docker inspect` that only diarygate volumes and the diarygate network are attached (the stack is taken down if not). `down.sh` copies logs out, runs `down -v --remove-orphans`, removes its own image tag and build context, then `isolation.py down` records `docker volume ls` / `docker network ls` showing nothing left. |
| `harness.py` | `init` (evidence directory), `load` (fixture through `PUT /api/file`, read back through `POST /api/file` and `GET /api/day?month=`), `mutate` (paraphrases and deletions through `POST /api/entries/edit`, corrections as a new entry on a later day), `queries` (`POST /v1/chat/completions`, signed tenant assertion, `entryTime` = the query clock). |
| `score.py` | One result per stage against `thresholds.json`; writes `matrix.csv` and `stages/score.json`. No blended score. |
| `rubric.json` | Fixed answer rubric; answer rows stay `needs-judge`. |
| `areas/*.py` | Ten workflow areas, each runnable on its own against its own synthetic tenant; each prints one JSON line (`pass`, `fail`, `blocked` or `untested`) with evidence paths. |
| `smoke.sh` | The no-inference smoke proof (below). |

Every script is standard-library Python or bash and runs on the MS-01 host with `python3 -I`; no venv.

## Tenant assertions

The harness acts as noevia web does: `Authorization: Bearer $DIARY_AUTH_TOKEN` plus
`X-Cowork-User-ID` and `X-Cowork-Tenant-Assertion: v2.<ts>.<nonce>.<sig>`, an HMAC-SHA256 with
`DIARY_TENANT_KEY` over the canonical string in `agent/tenant_assertion.py` (method, wire path, query
hash, body hash, storage header hash). `gatelib.sign` is checked against the diary's reference signer
in the tests. Each area uses fixed synthetic tenant ids (`gatelib.tenant_id`); the stack is fresh per run.

## Stages and thresholds (declared in `thresholds.json` before any run)

| Stage | Pass when | Needs |
| --- | --- | --- |
| candidate retrieval | Recall@8 >= 0.90 and Precision@8 >= 0.40 (precision over the candidates returned, at most 8) | retrieval trace |
| reranking | MRR no worse than the candidates and nDCG@8 >= 0.80, or `N/A: no reranker in diary` | trace with a `reranked` list |
| context load | recall >= 0.90 of relevant entries in the loaded context, every context within 5200 tokens | trace with a `context` list |
| answer | fact accuracy >= 0.90, citations >= 0.90, no stale facts, >= 5 of 6 abstentions, <= 1 false abstention | a judge (rows are `needs-judge`) |

The gate diary runs with `DIARY_RETRIEVAL_TRACE=1` and the harness sends `X-Diary-Retrieval-Trace: 1` on
every `/v1/chat/completions` call (services#107). It reads `retrieval_trace` (schema v1: `params`, `status`,
`rerank`, `candidates`, `loaded`, `budget`, `counts`, `direct_fallback`, and `focus` from services#116: the
`candidates` scored are those left after the diary's entity focus, its removals are listed in `focus.removed`). Trace `id`s are chunk rowids and
change on reindex, so candidates and loaded items are matched to truth entries by **day and HH:MM**
(the entry header's leading time); items on the empty query day (this session's own logged exchanges)
and any item carrying this exchange's xid are dropped. `rerank.present` is false in the diary, so the
reranking stage is `N/A: no reranker in diary`. A revision without the trace (for example the pre-release
diary) gives `trace unavailable` rows and `untested` retrieval stages; an unrecognised trace shape is
scored as untested too. The answer stage records deterministic signals from
The harness asks for a trace (`diary_trace: true`) and reads `diary.trace` (or `retrieval_trace`)
from the reply when the diary returns one; otherwise each row records `trace unavailable` and the
retrieval stages are `untested: trace unavailable`. It maps trace items to entry ids by xid, or by
document path and subsection header. The answer stage records deterministic signals from
`rubric.json` (expected facts, forbidden facts, cited day, abstention phrases) as *provisional*
numbers; there is no model judge.

## Load gate

Before **every** inference call and **every write that reindexes** (fixture load, read-back, mutations,
each restore: `PUT /api/file` and `/api/entries/edit` run `_reindex_dirty`, which embeds), the harness and
the model areas take `gatelib.inference_slot`: a cross-process `flock` (`GATE_LOCK_FILE`, default
`/tmp/diarygate-inference.lock`) held around the load check **and** the call, so no two gate processes
start inference work at once. The check re-runs up to `GATE_RECHECKS` (12) times `GATE_RECHECK_S` (5 s)
apart, so the previous turn's background reindex does not abort the run, then fails closed: they stop
(and write `blockers.md`) if the embed engine (`GATE_EMBED_LOAD_URL`), the aux engine
(`GATE_AUX_LOAD_URL`, skipped when it is the chat engine) or the chat engine
(`GATE_KEV_LOAD_URL`) has a request in flight (`/slots` `is_processing`, per loaded model), if
any load cannot be read, or if MemAvailable is under 6 GiB or unreadable. The token goes to every probe. Production containers are never
restarted, recreated or reconfigured by anything here.

## Workflow areas

| Area | Script | Model | Run |
| --- | --- | --- | --- |
| capture | `areas/capture.py` | no | parallel (own tenant) |
| tenancy | `areas/tenancy.py` | no | parallel (own two tenants) |
| semantic | `areas/semantic.py` | yes | parallel (own tenant and fixture copy) |
| temporal | `areas/temporal.py` | yes | parallel |
| corrections | `areas/corrections.py` | yes | parallel |
| follow-ups | `areas/follow_ups.py` | yes | parallel |
| confirmed-vs-inferred | `areas/confirmed_vs_inferred.py` | yes | parallel |
| restart | `areas/restart.py` | no | **alone** (restarts `diarygate-diary`, only after checking its compose project is `diarygate`) |
| error-paths | `areas/error_paths.py` | no | **alone** (deletes a tenant, probes limits) |
| budgets | `areas/budgets.py` | limits: no; context: yes | **alone** (limit-sized bodies, up to 64 MiB) |

Common flags: `--run-dir RUN` (required), `--fixture FIX` (model areas and budgets),
`--base-url` (default `http://127.0.0.1:18910`), `--env-file`, `--tenant-label`. Results go to
`RUN/workflows/<area>/result.json` and `requests.jsonl` (method, path, status and time only; no
headers or bodies). Without inference the model areas report `blocked`; with inference their answer
rows are `untested` (needs-judge) unless a request fails.

The no-model areas (capture, tenancy, error-paths, restart, the budgets limits) run against a second
diary, `diary-nomodel` on port 18911, whose chat, aux and embed URLs are always the disabled name, so
their writes can never start embedding work. Parallel model areas share the gate diary and the engines,
and the inference lock serialises their calls; "parallel" means their tenants are disjoint.

## Evidence layout

Written under the directory given by `--evidence-root` (refused inside a git work tree):

    release-evidence/diary-gate/<rev12>-<pre|post>/
      manifest.json         rev, phase, fixture tree hash, thresholds and rubric sha256, inference on/off
      fixture-manifest.json the fixture manifest
      matrix.csv            one row per stage and per workflow area
      stages/               load.json, mutations.json, answers.jsonl, traces.jsonl, answer-rows.json, score.json
      workflows/<area>/     result.json, requests.jsonl, answers.jsonl, load-gate.jsonl
      logs/                 isolation-up.json, isolation-down.json, diary.log, requests.jsonl, load-gate.jsonl
      blockers.md

## Smoke proof (no inference)

    cd diary/gate && ./smoke.sh ~/noevia-work/diarygate-evidence/smoke

Generates the fixture twice and compares bytes and tree hash; starts the stack with inference
pointed at an unresolvable name; loads the fixture through the API and reads every day back; applies
the scripted mutations; contaminates and restores the baseline (`harness.py restore-selftest`); runs capture and tenancy in parallel, then error-paths and restart alone;
records that the model areas are `blocked`; scores; tears down; and records `docker volume ls` and
`docker network ls` afterwards. It reads the production inference containers' start times before
and after (`logs/production-*.txt`) and never touches them.

## Running the gate before and after a release

1. Pick the revision with `up.sh --rev`: `pre` = the diary revision live now (for example services
   `2545ebc`, released in noevia `9375ce98`, which has no retrieval trace: its retrieval stages are
   `untested`), `post` = the release candidate (a revision that includes services#107).
2. On the MS-01, outside any production window, with the idle gate satisfied:

       cd ~/noevia-work/wt/<services worktree>/diary/gate
       GATE_LLM_BASE_URL=... GATE_CHAT_MODEL=... GATE_EMBED_BASE_URL=... GATE_EMBED_MODEL=... \
         GATE_LLM_API_KEY=... ./make_env.sh --force
       EV=~/noevia-work/diarygate-evidence
       python3 -I gen_fixture.py --out $EV/fixture        # once; the tree hash is in its manifest
       RUN=$(python3 -I harness.py init --evidence-root $EV --rev <rev> --phase pre --fixture $EV/fixture)
       ./up.sh --rev <rev> --run-dir $RUN
       python3 -I harness.py load    --run-dir $RUN --fixture $EV/fixture
       python3 -I harness.py mutate  --run-dir $RUN --fixture $EV/fixture
       python3 -I harness.py queries --run-dir $RUN --fixture $EV/fixture
       # workflow areas: the parallel group, then restart, error-paths and budgets one at a time
       python3 -I score.py --run-dir $RUN --fixture $EV/fixture     # again after judging
       ./down.sh --run-dir $RUN

3. Repeat with `--rev <candidate> --phase post` and the **same** fixture (same tree hash).
4. A judge reads `stages/answer-rows.json` and `workflows/<area>/answers.jsonl` and writes
   `RUN/judgements.jsonl`, one line per row: `{"row": <id>, "verdict": "pass"|"fail", "fact", "citation",
   "stale", "abstained", "judge": <role>}` applying `rubric.json`. `score.py` then computes the answer
   stage from the verdicts against `thresholds.json`, and a model area whose only open rows were
   needs-judge becomes pass or fail. The run verdict is never pass while any row needs a judge.
5. Compare `matrix.csv` pre and post row by row.
   A stage that regresses, or a workflow area that fails, blocks the release; `untested` and
   `blocked` rows are reported as such, never counted as passes.

Contamination: each `/v1/chat/completions` call is logged into the diary by design. After `mutate`
the harness snapshots the tenant (every file, plus the settled chunk count with inference) into
`stages/baseline.json`; after every query it PUTs back any changed file with its current version,
moves new files to Trash, waits for the journal and index to settle back to the baseline, and checks
the files match byte for byte (`logs/restore.jsonl`), stopping the run if they do not. The query
clock is an empty trailing day (day 61), so no fixture entry is "today" and logged exchanges land
on a day of their own. The diary's own clock is real time; the query clock is passed as `entryTime`.

## Parallel agent split

Six agents of the small, fast tier, one area group each, each with its own tenant label so no two
share data, all against the same stack and run directory:

| Agent | Areas |
| --- | --- |
| H1 | capture |
| H2 | retrieval: `harness.py queries` plus semantic and temporal |
| H3 | follow-ups |
| H4 | confirmed-vs-inferred |
| H5 | tenancy |
| H6 | corrections |

Then, serially and with no other agent running: restart, error-paths, budgets. Every agent stops
on a load-gate refusal and reports `blocked` with the reason; none restarts or reconfigures anything
outside the `diarygate` project.
